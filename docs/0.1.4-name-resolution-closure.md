# Reach 0.1.4 name-resolution observability closure

Version 0.1.4 turns hostname handling from "resolved / did not resolve" into
observable name-resolution facts: the source, the exact DNS query names, the
actual DNS server of an observed exchange whenever Reach can prove it, and
human-readable DNS results. It adds no new primary network protocol, no DNS
policy feature, and no new CLI shape. The authoritative product behavior
remains `network-diagnostic-cli-design.md`, now amended by its 9.5, 17.2,
17.3, 18.2, 18.8, and 21.1b clauses.

## Scope invariants

The TCP, ICMP, Neighbor, path, and failure-only Direct DNS state machines keep
their existing triggers, budgets, retries, concurrency, terminal priority, and
exit meanings. Command shape, stdout/stderr routing, exit codes 0/1/2/130,
elevation policy, and the no-external-command rule are unchanged. Successful
hostname checks gain no extra diagnostic DNS traffic.

## Typed name-resolution model

Core now carries `NameResolutionObservation { input_name, steps, limitations,
result }` inside the system resolver observation. A step has a typed source
(`Hosts`, `Dns`, `SystemResolverOpaque`, ...), the exact query names actually
used, observed formal DNS exchanges, and an outcome. A DNS exchange records an
explicit `FormalResolution | Diagnostic` purpose, the exact endpoint, the
observed transport, the wire query name, the query type, a typed outcome, and
timing. Configured candidates remain snapshot facts and can never be promoted
to an actual endpoint; a diagnostic exchange can never rewrite the system
resolver result or form a formal target.

Evidence moved from opaque strings to typed facts:
`EvidenceFact::NameResolution(NameResolutionEvidence)` and
`EvidenceFact::DnsExchange(DnsExchangeEvidence::{Formal, Diagnostic})`.

## Linux formal resolver

The static build still executes the host `hosts:` policy through `gai-core`.
The reached `dns` source now runs a bounded, Reach-controlled formal DNS
client built on the Hickory codec and Tokio sockets instead of
`hickory-resolver`, so every wire exchange is proven and recorded:

- resolver servers in resolv.conf order, per-server `timeout`/`attempts`
  honored with the resolv.conf defaults (5 s / 2);
- UDP with TCP fallback only on a truncated response;
- A and AAAA as independent query series; answer order and duplicates
  preserved (A answers first, then AAAA answers);
- glibc-style search/ndots candidate expansion, trailing-dot names never
  expanded, exact query names retained in semantic order;
- negative (NXDOMAIN/NODATA) results continue the search; a responding server
  terminates server iteration; a first failure on one series never erases an
  address returned by the other;
- unsupported resolv.conf options, scoped IPv6 nameservers, and reached
  unsupported NSS sources stay fail-closed required-capability errors.

The resulting step records the actual endpoint of every exchange, so a
`NAME RESOLUTION` report on Linux names the server that was really queried.

## Windows and macOS

The ordinary-user system resolver (`getaddrinfo` via `dns-lookup`) remains the
formal resolution path. Its exact DNS-server identity is not exposed, so the
platform reports an explicit capability boundary: no configured candidate is
relabeled as actual, and a later Reach-issued diagnostic exchange records only
its own exact endpoint with a diagnostic label.

## No-formal-target diagnosis

DNS dependency diagnosis now covers `SucceededWithoutUsableAddress`,
`NegativeWithoutUsableAddress`, and `NonDefinitiveFailure` whenever no formal
target exists and DNS diagnosis is semantically applicable. When the formal
resolution already produced observable DNS exchanges (Linux), those facts are
the failure localization and no extra diagnostic DNS traffic is sent. When
the formal path is opaque, the existing bounded Direct DNS dependency
diagnosis runs. Diagnostic addresses never become formal targets and never
start the requested TCP/ICMP check.

## Presentation contract

No-formal-target output is name-resolution-centric: `CHECK` uses
`Requested test` / `Result: Not started`, `NAME RESOLUTION` shows source,
actual DNS server(s), exact query name(s) (with `Input` when search
expansion changed the wire name), and independent A/AAAA summary lines.
`DNS DIAGNOSTIC` appears only when diagnostic DNS actually ran, and the
Direct DNS disclaimer in `WHAT THIS MEANS` is conditional on the same fact.
Common DNS results render as `NXDOMAIN`, `SERVFAIL`, `REFUSED`, `FORMERR`,
`NOTIMP`, `No A/AAAA address returned`, `Response truncated`, `Timed out`,
`Transport error`, and `Protocol error`; unknown codes stay numbered.
Durations use one shared formatter (`5 s`, `16 ms`, `1.2 s`). ICMP evidence
reads `ICMP Echo: Reply from ... in ...`. Default `EVIDENCE` never repeats a
fact already fully represented by `NAME RESOLUTION` / `DNS DIAGNOSTIC`;
capability-boundary facts remain visible. Clean success stays compact: a
proven DNS server appears as one CHECK line, a hosts hit shows
`Name source: hosts`, and IP-literal output contains no name-resolution
section.

## Release gates

The unchanged six-target matrix remains the release gate: `x86_64`/`aarch64`
`unknown-linux-musl` static ELF, `x86_64`/`aarch64` `apple-darwin` single
Mach-O, and `x86_64`/`aarch64` `pc-windows-msvc` with static CRT, one
executable per archive, inspected before and after packaging, with version,
invalid-input, IPv4-loopback TCP, and `localhost` smoke tests against the
extracted artifact. `cargo fmt`, clippy with `-D warnings`, the workspace
test suite, `cargo audit`, `cargo machete`, external-process prohibition,
and persistent-mutation prohibition remain required. The exact unpinned
stable Rust toolchain actually used is recorded in the release provenance.
