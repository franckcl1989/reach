# Reach 0.1.0 native capability matrix

This matrix implements the real-system evidence requirement in design section
23.4. `Available` and `Unavailable` below are product capability states, not a
quality ranking. An honest `Unavailable` is required when the ordinary-user OS
surface cannot provide the exact observation semantics.

## Adapter contract (not native release evidence)

The entries in this table describe which adapter is intended to produce a
capability state. They do **not** by themselves assert that a
platform/architecture passed its native release gate. Only the native
execution status table below records verified release evidence.

| Capability | Linux adapter | macOS adapter | Windows adapter |
|---|---|---|---|
| Interface snapshot | `netdev` | `netdev` | `netdev` |
| Route snapshot | `rtnetlink` | `netroute` | `netroute` |
| Resolver configuration snapshot | `resolv-conf` + `gai-core`; classic direct-DNS candidates require an explicit NSS `dns` source | `system-configuration`; malformed endpoint fields remain limitations and real transport remains Unknown where the public dynamic store does not prove it | `ipconfig`; real transport remains Unknown where Windows does not expose it |
| Current targeted path | Explicit Unavailable boundary: destination-only `RTM_GETROUTE` cannot prove the later socket's flow-dependent selection | Explicit Unavailable boundary: no selected mature ordinary-user API proves the required traffic-free query | `GetBestRoute2` |
| Neighbor read | `rtnetlink` | Explicit Unavailable boundary: no selected mature ordinary-user reader provides the required exact lookup | `GetIpNetEntry2` |
| TCP Connect | Tokio | Tokio | Tokio |
| ICMP Echo | `surge-ping` datagram ICMP | `surge-ping` datagram ICMP | Windows IP Helper |
| ICMP TTL/Hop-Limit path correlation | Explicit Unavailable boundary | Explicit Unavailable boundary | Explicit Unavailable boundary |
| TCP TTL/Hop-Limit path correlation | Explicit Unavailable boundary | Explicit Unavailable boundary | Explicit Unavailable boundary |
| Direct DNS UDP/TCP | Tokio sockets + Hickory codec; invoked only for a proven classic transport | Same | Same |
| Cancellation | `CancellationToken`; OS resolver worker may detach | Same | Same |

The path-correlation states are explicit because no selected mature
ordinary-user mechanism can reliably correlate router-originated responses to
the exact originating Attempt. Reach does not substitute another protocol,
elevate, invoke an external program, or rewrite the already-established
primary result.

## Native evidence tests

The CI workflow runs these tests without elevation and with `--nocapture`:

- `native_snapshot_capabilities_are_observed_and_reported`
- the Windows `targeted_loopback_path_uses_read_only_kernel_query` test or the Linux/macOS explicit-boundary test
- `passive_missing_neighbor_is_an_available_unknown_fact` or the macOS explicit-boundary test
- the IPv4 and IPv6 ordinary-user loopback TCP tests
- the Windows or Unix IPv4 and IPv6 ordinary-user loopback ICMP tests
- `unproven_path_correlation_is_an_explicit_native_capability_state`
- IPv4 and IPv6 direct DNS UDP/TCP local-server coverage
- `ordinary_user_system_resolver_resolves_localhost`
- `cancellation_preempts_the_os_resolver_without_a_product_timeout`
- bounded real child-process console-interrupt coverage
- continuous-clock and suspend-style deadline tests
- CLI success, failure, invalid-input, help, and output-routing process tests

The GitHub-hosted runner labels are defined in `.github/workflows/ci.yml`.
Every native job built, executed, and archived exactly the platform's single
`reach` executable in the recorded release run.
