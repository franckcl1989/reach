# Reach 0.1.1 output contract

Version 0.1.1 changes presentation only. The 0.1.0 diagnostic state machines,
probe order, deadlines, capability boundaries, aggregation, and exit meanings
remain unchanged.

## Audiences and reading order

One report must work for two audiences without requiring an extra flag:

1. A non-technical user must understand the answer from the title and the
   short explanation immediately below it.
2. A support person or network engineer must be able to use the same copied
   report without asking the user to reproduce the check in another mode.

Every completed report therefore uses progressive disclosure:

1. plain-language verdict;
2. what Reach checked and what the result means;
3. every resolved target and its independent result;
4. cautious next steps when the check is not cleanly satisfied;
5. exact resolver, route, Neighbor, capability, and Attempt facts under
   `Technical details`;
6. Reach version, platform, and exit code.

## Language rules

- User-facing text must not expose Core vocabulary such as `formal target`,
  `aggregate outcome`, `primary decision`, or `CapabilityValue`.
- `satisfied` is replaced with the concrete operation that succeeded or
  failed: TCP connection, ICMP Echo, or name resolution.
- A retry is always numbered. Two identical timeouts must never appear as two
  indistinguishable lines.
- ICMP success is never described as proof that a website or TCP service works.
- TCP success is never described as proof that an application protocol works.
- A timeout never proves that a port is closed, a host is down, or a firewall
  is the cause.
- A refusal may come from the destination or an intermediate device and must
  not be presented as proof that an application is not listening.
- Unknown, unavailable, failed, refused, timed out, and cancelled remain
  distinct states.
- Advice may tell the user what to verify or whom to contact, but may not claim
  an unobserved root cause.

## Completeness rules

- Every unique target produced by the system resolver is shown in resolver
  order, even when several targets have the same result.
- The friendly target summary never replaces technical facts.
- Technical details include every executed Attempt with its order, exact kind,
  exact observed outcome, elapsed duration, and deadline budget.
- Relevant initial/current path, matching route, Neighbor, diagnostic-boundary,
  capability-limitation, and resolver-dependency facts are retained.
- Resolver output distinguishes returned records from unique addresses checked
  and lists the returned addresses in order.
- Untrusted operating-system and network text is terminal-safe and cannot add
  lines, ANSI state, or bidirectional controls.

## Output and terminal behavior

- Completed diagnostics, including exit 1, are written to stdout.
- Invalid input and execution errors are written to stderr with a plain title,
  explanation, safe technical reason, suggested action, usage when relevant,
  and the exit code.
- Cancellation is written to stderr and remains exit 130.
- TTY output may use color and a transient spinner through mature terminal
  libraries. Redirected output contains no ANSI sequences and no progress.
- Unicode structure and status symbols carry no information that is absent
  from their accompanying words.
